# FactoryTwin Copilot

A real-time **Smart Factory Digital Twin** in Neo4j, and a chatbot copilot that lets an engineer talk to
the factory in natural language. It answers with three techniques and shows how it did so:

| Question type | Technique | Example |
|---|---|---|
| Facts, counts, live state, relationships | **Text2Cypher** (read-only, guarded) | *Which machines on Line A2 have open alarms?* |
| Procedures, specs, error codes | **Vector + keyword RAG** over manuals, SOPs, troubleshooting guides | *How do I replace a worn spindle bearing on a model3 machine?* |
| Diagnosis | **Hybrid GraphRAG**: live context + similar past failures + manuals + `FEEDS_INTO` downstream | *Machine 17 is vibrating. What is the likely cause and what is affected downstream?* |

Every answer has a collapsible **"How I answered"** panel: route, tools, the Cypher, sources, latency,
tokens and estimated cost.

> **Synthetic data.** Telemetry, errors, maintenance and failures come from the Microsoft Azure
> Predictive Maintenance dataset, which is itself synthetic. Plants, lines, topology, technicians,
> thresholds and **all RAG documents** are generated by this project (the documents by an LLM, from the
> real data). Every generated node and document carries `synthetic: true`. Nothing here describes a real
> factory.

Full specification: [docs/PROJECT_SPEC.md](docs/PROJECT_SPEC.md) · contributor notes: [CLAUDE.md](CLAUDE.md)

## Architecture

```
┌──────────────────────────── Angular frontend (:4200) ────────────────────────────┐
│ Dashboard │ Machine detail │ Graph explorer │ Simulator panel │ Chat drawer      │
└───────────────┬───────────────────────────────────────┬──────────────────────────┘
                │ REST /api/*                           │ WebSocket /ws/chat, /ws/events
┌───────────────▼───────────────────────────────────────▼──────────────────────────┐
│ FastAPI backend (:8000)                                                          │
│  chat/       orchestrator: OpenAI tool-calling loop (≤4 rounds) → streamed answer│
│  retrieval/  text2cypher + cypher_guard · hybrid RAG · similar incidents · context│
│  streaming/  MQTT consumer (lifespan task) · alarm engine · WS broadcaster       │
└───────┬──────────────────────────────────────────────▲───────────────────────────┘
        │ Bolt                                         │ MQTT subscribe
┌───────▼──────────────┐                  ┌────────────┴───────────┐
│ Neo4j Community      │                  │ Mosquitto (:1883)      │
│ graph + vector +     │                  └────────────▲───────────┘
│ fulltext indexes     │                               │ MQTT publish
└──────────────────────┘                  ┌────────────┴───────────┐
                                          │ Simulator (own process)│
                                          │ replays the CSVs       │
                                          └────────────────────────┘
```

**How a question is answered.** An orchestrator model (OpenAI tool calling) picks among four tools:
`query_twin_data` (Text2Cypher), `get_machine_context` (fixed hand-written Cypher),
`search_knowledge_base` (hybrid vector + fulltext RAG) and `find_similar_incidents` (vector search over
past failures, then graph traversal). The tools it chose determine the route (`cypher`, `rag`, `hybrid`,
`direct`). A second model call writes the answer **only from the tool results**, with `[n]` citations,
and streams it to the browser.

**How the live twin works.** The simulator publishes one reading per machine per tick over MQTT. The
backend batches messages once per second, updates `Sensor.latest_value`/`avg_24h`, and runs a debounced
alarm engine (3 consecutive breaches open an alarm, 5 normal readings clear it). A new alarm is
embedded, linked to the three most similar past failures (`SIMILAR_TO`), broadcast on `/ws/events`, and
pushed into every open chat as a proactive message.

## Setup (macOS)

```bash
brew install python@3.12 uv git node
brew install --cask docker               # or OrbStack / Colima; give it at least 4 GB RAM
uv tool install kaggle                   # needs ~/.kaggle/kaggle.json (free Kaggle account)
```

You need an OpenAI API key with prepaid credits (a ChatGPT subscription does not include API usage).
Set a monthly spending limit in the OpenAI dashboard.

```bash
cp .env.example .env                     # set NEO4J_PASSWORD, OPENAI_API_KEY and the OPENAI_*_MODEL values
docker compose up -d                     # Neo4j (7474/7687) + Mosquitto (1883)

# 1. data
kaggle datasets download -d arnabbiswas1/microsoft-azure-predictive-maintenance --unzip -p data/raw
cd backend && uv sync
uv run python -m app.ingestion.run_all --skip-embeddings    # schema, topology, history, thresholds (no OpenAI)
uv run python -m app.ingestion.generate_documents --dry-run # shows the planned documents and an estimated cost
uv run python -m app.ingestion.generate_documents           # ~130 documents via OPENAI_CHEAP_MODEL (skips existing)
uv run python -m app.ingestion.run_all                      # + chunk/embed documents and failures

# 2. run
uv run uvicorn app.main:app --reload                        # API on :8000
uv run python -m app.streaming.simulator                    # sensor simulator (separate terminal)
cd ../frontend && npm install && npm start                  # Angular on :4200, proxies /api and /ws
```

Open <http://localhost:4200>. Ingestion is idempotent: re-running creates no duplicates and embeds only
changed documents. Generated documents are meant to be committed (`data/generated/docs/`) so others do
not have to regenerate them.

## Evaluation

`backend/eval/questions.yaml` has 45 questions (15 Text2Cypher, 15 RAG, 15 hybrid). The harness reports
route accuracy, Cypher execution and result accuracy against gold queries, RAG hit@5, answer keyword
recall, p50/p95 latency and cost per question, plus optional model and retrieval-mode comparisons, in
`eval/report.md`.

Results of two consecutive runs of the same 45 questions (`backend/eval/report.md` holds the latest;
`gpt-6-luna` for every role, `OPENAI_REASONING_EFFORT=low`, `text-embedding-3-small`, RAG cutoff 0.68).
Run B came after a few more prompt rules (read-only, stay in scope); nothing else changed.

| Metric | Run A | Run B |
|---|---|---|
| Route accuracy (cypher / rag / hybrid) | 100% (15/15 each) | 100% (15/15 each) |
| Cypher executes without error | 100% | 100% |
| Cypher result accuracy, **lenient** (every gold value is in the result) | 100% | 100% |
| Cypher result accuracy, **strict** (identical result set) | 60% | 47% |
| RAG hit@5, hybrid retrieval alone (no LLM involved) | 100% | 100% |
| RAG hit@5, through the chatbot | 100% | 94% |
| Expected tools used | 100% | 93% |
| Answer keyword recall | 98% | 98% |
| Latency p50 / p95 | 7.0 s / 18.4 s | 7.8 s / 23.2 s |

How to read this honestly:

- **Strict vs lenient.** The strict metric fails a query that returns the right numbers plus an extra
  column (a machine id beside a count, a plant name where the gold query used an id). Reading all
  mismatches, every answer was correct, and strict accuracy changed on 6 of 15 questions between two
  runs, so it mostly measures how verbose the model's query is. The lenient metric is the one that tracks
  correctness; both are reported.
- **Small sample, noisy.** 45 questions and a non-deterministic model: the two runs differ by a few
  questions in both directions (for example the model sometimes words its search so the model3 manual
  is not retrieved, and sometimes answers a hybrid question with the Cypher tool instead of the
  machine-context tool). Treat differences of a few points as noise. The first run scored 96% routing, 67% strict Cypher accuracy and 94% hit@5; the
  second, after fixes made in response (name-not-code rule in the Cypher prompt, "what is common/usual"
  questions go to the knowledge base, `gold` for c01 changed to the plant name), scored the numbers
  above. The questions were visible while tuning, so treat the second run as optimistic.
- **Vector-only matches hybrid here** (100% each): the corpus is small (147 chunks) and the questions are
  worded like the documents. This comparison would only separate the two on a larger or noisier corpus.
- **Cost is not reported**: set `PRICE_INPUT_PER_M` / `PRICE_OUTPUT_PER_M` in `.env` (I did not know the
  prices of the configured model) and re-run to fill in the cost rows.

## Design decisions

- **Telemetry stays out of the graph.** Raw readings would grow it without bound and add nothing the
  questions need. The graph holds the latest value and a 24-reading average per sensor; the last 200
  readings per sensor live in an in-memory ring buffer for charts.
- **LLM-generated Cypher is read-only, twice.** `cypher_guard` rejects write/admin clauses (outside
  string literals, comments and backticks), multiple statements and procedure calls, caps results at 50
  rows, `EXPLAIN`s the query and executes it in a READ transaction with a 10 s timeout. Community
  Edition has no role-based access control, so this is the protection layer. One retry feeds the error
  back to the model.
- **Fixed Cypher where the question is predictable.** "Everything about machine M017" is always the same
  shape, so `get_machine_context` is hand-written and tested rather than generated: it is cheaper,
  faster and cannot be wrong in a new way each time. Text2Cypher is for the open-ended questions.
- **The route is implicit in tool choice.** There is no separate classifier call; the tools the model
  picks are the route, which keeps the trace honest and avoids a second source of disagreement.
- **Answers come only from tool results.** The answer prompt forbids outside knowledge; if retrieval
  finds nothing above `RAG_MIN_SCORE` the tool says so and the answer says "I don't know". The similarity
  score is Neo4j's `vector.similarity.cosine`, i.e. `(1 + cos) / 2`. The spec suggested 0.75, but measured
  on this corpus with `text-embedding-3-small`, off-topic questions top out at 0.64, short on-topic
  queries ("bearing overheating") score 0.70-0.79 and full questions 0.76-0.87, so the default is 0.68.
  Re-calibrate if you change the embedding model or the documents.
- **Stable prompt prefixes.** System prompt, schema and few-shot examples are identical across requests
  so OpenAI prompt caching applies; embeddings are cached on disk by content hash.
- **Retrieval is synchronous, the API is async.** `neo4j-graphrag` retrievers use the sync driver, so the
  chat tools run in worker threads on a process-wide sync driver while REST/streaming use the async one.
- **Sensor-document consistency.** Manuals are generated from the same thresholds the alarm engine uses,
  and component names come from a single constant, so a manual's "normal range" matches what raises an
  alarm.

## Cost notes

Costs depend on the models you configure in `.env` (names are never hardcoded; set
`PRICE_INPUT_PER_M`/`PRICE_OUTPUT_PER_M` to see estimates). Document generation is the main one-off
cost: run `generate_documents --dry-run` first. After that, a chat request is one planning call, 0-4
tool rounds (Text2Cypher adds one model call) and one streamed answer call; the trace shows the exact
tokens and estimated dollars per request.
